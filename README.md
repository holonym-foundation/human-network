# Human Network
## About
Human Network is a "blind", decentralized elliptic curve point by scalar multipication network. It acts as a decentralized base layer for protocols that require threshold scalar multiplication. It simply multiplies an input point, which can be information-theoretically masked, by a private key shared by the network. Standard threshold cryptography is used to ensure that no node can see the private key unless a sufficient fraction of the network is compromised.

## Use cases
### To Secure Identities, Keys, and/or Nullifiers using an Oblivious Pseudorandom Function
The most immediate use case of Human network is using it to decentralize a 2HashDH oblivious pseudorandom function. This applies a pseudorandom function (PRF) to an insecure input like a password or biometric identity. These inputs lack entropy so simply hashing them is not possible to do securely; revealing their digest leaves them open to to bruteforce or often dictionary-like attacks.

Enabling the ability to securely make random "digests" from low-entropy secrets enables use cases such as 
- secure private keys from passwords
- truly private biometrics
- decentralized wallet recovery from biometrics, security questions, or other memorable data
- nullifiers for zero-knowledge proofs (ZKPs) of identity generated by name, date of birth, and other low-entrpoy identifiable information.

### To Enable an Ideal Tradeoff of Privacy and Compliance In Zero Knowledge Identity Protocols
Human Network supports a variety of curves including [BabyJubJub](https://eips.ethereum.org/EIPS/eip-249). With BabyJubJub point-scalar multiplication, efficient client-side provable encryption within a general-purose zero knowledge proof is possible. This enables a user to effiently prove they have encrypted data to Human network, and that the data has certain properties. Human network can then reveal encrypted data to the authorized parties only under a decentralized rulebook, where nodes must agree on predefined decryption conditions. Currently, to give regulators access to user data, companies must log all user data. This frequently compromises security and privacy to data breaches targeted advertising. Provable encryption with set rules for decentralized for decryption strikes a middle ground where ordinary users retain privacy while companies retain the ability to comply with laws.

# Network Preliminaries
## Epoch
To save time and coordination / gas fees, nodes only communicate in transition periods between epochs. Epochs are set periods of time in which global network state, but not necessarily local node state is constant. I.e.
- The number of requests each user has made to the network is not globally agreed upon. Rather, each node has knowledge only of the requests they have received. 
- The threshold does not change

## Elliptic Curve Math
Explaining elliptic curves is not in the scope of these docs. [Here is a great resource for learning](https://blog.cloudflare.com/a-relatively-easy-to-understand-primer-on-elliptic-curve-cryptography)

## 2HashDH Oblivious pseudorandom function (OPRF)
2HashDH is similar in that it the "server" only uses the private key to do a scalar multiplication, just like the "reciever" in ElGamal encryption.

2HashDH efficiently computes a pseudorandom function on an input $x$ that is not necessarily random or high entropy using server secret $k$. The client does not learn $k$ and the server does not learn $x$, but the client can learn $PRF(k,x)$. Even if $x$ has limited possibilities, the resulting value cannot be bruteforced to learn x without knowledge of $k$. 

The PRF in 2HashDH is 
```
hashToScalar(
    k * hashToCurve(x)
)
```

As in ElGamal decryption, the only step that requires a secret key is multiplying the secret key by a point on an elliptic curve.

## ElGamal Encryption
Assuming some function `mapToCurve(Scalar) -> Point` easily reversible so that the original scalar can be recovered from the resulting point.

In ElGamal, the receiver has a private key $a$ and public key $A = aG$ where $G$ is the generator point.
The sender chooses an ephemeral private key $b$ and public key $B = bG$, then computes the shared Diffie Hellman secret: $abG$. The ciphertext is just $mapToCurve(msg)$ blinded by the shared secret$abG$, along with $B$ to allow Diffie Hellman recovery of the shared secret.
cipheretext = $(B, mapToCurve(msg) + abG)$

To decrypt, the receiver can also do the scalar-point multiplication from Diffier Hellman to arrive at the shared secret $abG$. Then, they  subtract this to arrive at mapToCurve(msg), which they convert back into the original msg.

## Threshold Cryptography
Scalar-point multiplication can be decentralized  by the following:
### DKG
Standard DKG where node $i$ learns an additive share $f_i$ of some secret polynomial $f$, along with $f(i)$. $f(0)$ is the private key of the network. The threshold $t$ of $n$ nodes who can collective act on behalf of the network is determined by the degree of polynomial $f$.
### Multiplication
If user requests to learn some point $P$ multiplied by the private key $f(0)$, one simply sends $P$ to $t$ nodes who all return $f(i) * P$ and a DLEQ proof of correct multiplication. 

I.e., each node sends $S = f(i) * P$ and a DLEQ proof that both: 
- its response $S = f(i) * P$ 
- its public key $K_i = f(i) * G$

 are for the same $f(i)$.

_Note: these nodes behave identically as how they would in the centralized case, except instead of multiplying their private key by $P$ they multiply their private key share, $f(i)$, by $P$._

After recieving the multiplications and verifying their DLEQ proofs (see the Verify section), the user computes $f(0) * P$ with Lagrange interpolation:
$f(0)*P = \sum{l(i)*f(i)*P}$ where $l$ is a publicly known function for giving each node Lagrange coefficients.

_Note: $l(i)$ is the "Lagrange basis at 0". I.e., if $l_{i, S}$ is the Lagrange basis for node $i$ in set of nodes $S$, l(i) is $l_i(0)$._

### Verification
To ensure nodes can be held accountable for giving an invalid result of $f(i) * P$ a discrete-log equality proof is used to check their results are all right. Otherwise, a malicious node could untraceably cause the netowrk to give incorrect results. With this accountability, nodes are incentivized to give the right result since if they are known to be unreliable, users will not use them and they would not collect any fees from users.

To verify the proofs, the relayer verifies the DLEQ proof and also checks public outputs. To check its public outputs The user must check that the two points in the proof are the node's actual response and actual public key $K_i$.

## Option for semi-trusted ndoes
Collusion is an issue for threshold protocols; no social consensus can undo the harm of stealing the network's private key. Thus, it is reccomended to use a semi-trusted node if there is concern the network may be compromised. Semi-trusted nodes are not party of the network. They are addons users can elect for additive secret sharing. In the case of semi-trusted nodes, the private key is split into two additive shares: the network share and the semi-trusted node's share: $f(0)$ + $s$. The result of scalar multiplication by point $P$ is simply
$f(0) * P$ + $s * P$. Thus, semi-trusted nodes are entirely independent of the network. Anyone can run a semi-trusted node and users can opt-in to any semi-trusted node.


## Coordination
A distributed hash table and a relay node are used for coordination. Most network activity is asynchronous for scalability. user requests are sent to the relay node which then forward request to relavent nodes, interpolates their responses, and returns the result back to the user. This allows efficient performance even with a high number of nodes and users.

Some network functions need communicatoin: to add and remove nodes from the network, a resharing protocol is done to reshare the same secret to a new quorum at each epoch. At each epoch, the global ledger of how many requests each user has made is also agreed upon by the network and stored on a data availability layer.

Testnet version I does not have changing epochs and therefore no resharing and accounting consensus.

## Fees
Users buy credits on-chain. Nodes run Ethereum light clients so they can know the balance of each user. They locally cache requests the user has made in the epoch. Nodes do not respond to requests that would let the number of items in this local cache exceed the on-chain balance of user credits. 

Operator rewards will be paid from the purchase of credits, along with a capped amount of inflation of the $HUMAN token supply to meet n `minEpochReward`. PoW-like rewards will be given to incentivize nodse to respond:
1. Relay node commits to all (request, responses) tuples in each epoch
2. A random number is chosen after the commitment
3. The commitment is opened to a random response and if the response contains a valid proof, the relayer and provers involved will recieve a reward.
These are not implemented in testnet and not in mainnet until after EigenLayer operator rewards are live. 

## Accounting
The relay node posts the sigantures of all requests in batches of `TASK_SIZE`to IPFS, and sends the IPFS CID to Othentic attestors. They produce a weighted-by-stake aggregate BLS signature of this IPFS CID, insofar as the CID contains only valid request.

When Eigenlayer includes operator rewards, this accounting is used to determined the reward amount to the current oeprator set.

# Testnet Architecture
## Custom nodes
The Prover, Verifier, Relayer, and Test Telemetry are types of nodes built from the rust binaries in this project. The Prover nodes do multiplications and their corresponding DLEQ proofs and the Relayer relays requests from users to a set of Provers. If the Relayer reaches a certain number of requests, currently set to 1000, it sends a task proof to the verifier nodes (via the Othentic RPC and AVS WebAPI nodes, described later on). This task proof just proves there have been a certain number of signed requests sent to the network. It doesn't prove the network has responded -- there are future incentive mechanisms to respond which provide cryptoeconomic trust that the network will respond.

The Test Telemetry node is used for tests, so logs across all nodes are shared in a centralized place.

## Othentic nodes
The AVSWebAPI, Attestor and Aggregator are nodes provided by Othentic. Attestors attest to validity of task proofs with BLS signatures and Aggregators combine these signatures to one signature, posting the one signature on-chain. Attestor images do not directly validate the signatures. Rather they query AVSWebAPI images, which in our case are just images of Verifier nodes. AVSWebAPI is more an interface, specifying a certain endpoint it has to respond to in a certain way, and the Verifier node implements this interface.

Essentially Attestor, AVSWebAPI, and Verifiers are all the same -- each Attestor should run an AVSWebAPI container which is a Verifier.

## How to be an Operator
Most nodes will be prover nodes. To run any type of node, simply
1. Ask the team for the relevant envirnoment variables and save as .env.
2. Set `RSA_SEED` and `SECP256K1_SEED`. Each must be a 32-byte hex string without a 0x prefix.
3. Give the team your docker hub email address or username so we can give you access to the docker image
4. Setup your operator via `docker run -it mishtinetwork/operator othentic-cli operator register`. Use the AVS governance contract address `0x8F02dAC5E2FA7ee3f8B40A62e374093A120f90Ae`

### Running a Prover node

#### Register

First register with the Human PeerRegistry smart contract. \<rpc-url> must be a URL for a Holesky RPC node, used to send the registration transaction to the blockchain. \<private-key> should be for the account you want to associate with your node metadata. \<multiaddr> and \<rpcaddr> should be the multiaddr and RPC address of your Human node.

    docker run --env-file .env mishtinetwork/operator ./registry_iface register --rpc-url <rpc-url> --private-key <private-key> --multiaddr <multiaddr> --rpcaddr <rpcaddr>

If the call is successful, you will see a transaction receipt.

When populating your environment variables, make sure your multiaddr and rpcaddr match what you registered.

#### Run

    docker run --env-file .env --restart="always" mishtinetwork/operator ./human_node --bootstrap-peer-id <bootstrap-peer-id> --bootstrap-multiaddr <bootstrap-multiaddr> --relay-peer-id <relay-peer-id> --relay-multiaddr <relay-multiaddr> --port <port> --redis redis://127.0.0.1:6379/0

### Running an AVSWebAPI/Verifier/Attestor node
You will need two docker images running locally: 
- `docker run --env-file .env --restart="always" mishtinetwork/operator sh -c 'redis-server --daemonize yes; ./verifier'`
`docker run --env-file .env --restart="always" mishtinetwork/operator othentic-cli node attester /ip4/<bootstrap node IP address>/tcp/9876/p2p/<Othentic bootstrap ID> --avs-webapi http://0.0.0.0`

For testnet, the bootstrap node IP address is `52.90.236.173` and bootstrap ID is `12D3KooWCvMcbwgVsf6TgCGLN5o64WBWrJnuZLJYizy4hHkRAma5`.
### Running the Aggregator node
`docker run --env-file .env --restart="always" -p 8545:8545 -p 9876:9876 mishtinetwork/operator othentic-cli node aggregator --json-rpc`
### Running the Relay node
Follow the steps in "Running a Prover node", but set the `NODE_TYPE` environment variable to `Relay`.
